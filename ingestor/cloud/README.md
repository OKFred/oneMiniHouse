# 原始数据云副本

Worker 将最多 32 条原始记录写入 `RAW_DB`，收到事务成功确认后才返回原始 ID 与 SHA-256。认证 secret、站点范围、原始数据格式、不可变字段和最长 180 天的请求保留协议沿用既有约定；D1 副本可以配置更短的保留期，不会将投递失败当成成功或伪造新记录。

## 保留满库并继续写入

可选绑定 `RAW_DB_ARCHIVE_1` 至 `RAW_DB_ARCHIVE_9` 用于保留此前的原始副本。没有这些绑定时维持原先的单库行为。配置格式见 [wrangler.rollover.example.jsonc](wrangler.rollover.example.jsonc)；它仅包含合成项目名和占位 ID，不能直接覆盖线上私有配置。

切换时先创建并迁移新的数据库，将其绑定为 `RAW_DB`，把原 `RAW_DB` 保留为一个历史绑定。每个历史库均须具备 `migrations/0001_raw_archive.sql` 与 `0002_replay_timestamps.sql` 的表结构。切换后其他写入器也应停止向历史库新增原始数据；历史库继续执行当前配置的过期清理。保留当前 Worker 地址、站点配置、Cron 与 `ARCHIVE_TOKEN`，不要重置入库队列或消息 ID。此功能不会自动创建数据库、自动切换或提高账户总容量及每日额度。

收到批次后，Worker 依次对每个历史库执行一次 `raw_id IN (...)` 主键查询。所有历史查询成功后才向当前库插入未命中的记录：

- 历史库已存且全部不可变字段相同：按原 ID/哈希确认，不在当前库重新保存，也不延长历史过期时间。
- 任一历史或当前副本含同 ID 的不同内容、身份或生成时间：整批返回 `409`，不写入本批新记录。
- 任一历史查询失败：整批不确认、不写新库，由入库端保留队列并重试。

比较字段严格对应 `0002_replay_timestamps.sql` 的 trigger，包括原始文本、哈希、来源类型、来源 ID、主题、数据类型、内容类型、生成时间，以及消息／站点／网关／设备标识。查询使用严格相等比较，并区分 `NULL`。`receive_time_utc`、`store_time_utc`、`expire_time_utc` 和 `mirror_store_time_utc` 属于第一次保存的副本时间，允许重放请求携带不同值，但已有副本的值不会更新。仅比较哈希不足以确认同一原始来源。

历史库命中的 ID 还会在当前库查一次，以检测已有双份记录是否冲突；新记录继续由当前库的 trigger 和 D1 batch 事务防止并发冲突。每库返回最多 32 条记录，历史查询串行执行。最多九个历史库时，单次请求最多使用 41 条 SQL 查询：未命中时为 9 次查询加 32 次插入；有历史命中时额外一次当前库查询，但插入数量至少减一。参见 [D1 batch 事务](https://developers.cloudflare.com/d1/worker-api/d1-database/)及 [D1 限制](https://developers.cloudflare.com/d1/platform/limits/)。

## D1 保留策略

可选环境变量 `D1_RETENTION_DAYS` 取整数 `1` 至 `180`，可以是数字或数字字符串；未设置时默认 `180`，兼容原部署。示例中设置 `"7"`。非法值会让已认证写入返回 `503 not_configured`，Cron 在执行 SQL 前失败，不会静默采用更长保留期。

新记录的 D1 过期时间是 `min(请求 expire_time_utc, store_time_utc + D1_RETENTION_DAYS 天)`。以原始保存时间 `store_time_utc` 为起点，不使用设备生成时间、云镜像写入时间或重放到达时间；调用方更短的过期时间仍有效。重放已存 ID 不修改第一次保存的时间字段。该设置只作用于 D1，不缩短本地 SQLite 原始历史、本地 PostgreSQL 或 Supabase 的保留策略，也不要求修改入库端的 180 天请求配置。

超过 D1 保留窗口才送达的队列记录仍会真实写入 D1，并在事务成功后按原 ID／哈希确认；它们可能已经到期，由后续清理删除。不会伪造成功确认、改写消息 ID 或丢弃调用方待发队列。

缩短保留期也适用于已存的 180 天记录，包括历史绑定中的记录。它们的原始时间值不批量改写；清理使用原 `expire_time_utc` 与 `store_time_utc + 当前窗口` 中更早者。这个操作会删除到期的 D1 副本，延长窗口或回退代码不能恢复已删除的数据。确认保留要求后再启用，必要的恢复材料保存在独立位置。

### 上线前核验

不新增索引、游标表或历史库偏移配置。默认 180 天策略的当前库，以及所有历史绑定，必须有建库迁移创建的 `raw_message_expiry`，首列为 `expire_time_utc`；部署前核对其定义。短策略的当前库按 `rowid` 批删，不依赖过期索引。既存记录也必须符合原请求合同 `expire_time_utc <= store_time_utc + 180 天`，新请求继续强制这一约束。不要未经检查把不符合合同的外部表直接绑定进来。

可选迁移 `0003_archive_write_budget.sql` 删除 `raw_message_device_time` 索引，以减少每次插入的索引写计量。这个 Worker 的接口仅按主键查重、按过期索引清理，没有按设备／生成时间读取的接口；原始表、记录、主键和过期索引保留。若其他业务依赖设备时间查询，应先核对实际查询计划，再选择是否应用该迁移。应用后也要按真实 D1 `meta.rows_written` 和账户计量核验节省量，不能只按索引个数估算。

短策略的当前续写库还可以在保存索引定义、核对其他查询用途后单独移除 `raw_message_expiry`，进一步减少新增写计量；这不属于默认迁移，默认 180 天模板仍需过期索引。历史库继续保留它。回退到 180 天，或把无过期索引的当前库转为历史绑定前，必须恢复并核验该索引，且评估回填的容量与配额；不能直接互换绑定后假设历史清理仍然可用。

### 有界过期清理

默认 180 天仍使用原来的过期索引查询。短策略的当前库用 `rowid IN (SELECT rowid ... ORDER BY rowid LIMIT ...)` 删除保存窗口已超时、或实际过期时间已到的记录；这允许移除当前库的过期索引，不增加持久化游标或元数据表。

短策略的历史库继续复用过期索引：先限定 `expire_time_utc < 当前时间 + (180 - 保留天数) 天`，再用 `store_time_utc < 当前时间 - 保留天数` 或实际 `expire_time_utc < 当前时间` 作为删除护栏。由最长 180 天合同可证明，超保存窗口的记录一定落在这个过期时间范围；较早的实际到期记录也会命中。不需要改写旧过期时间，也不需要对满库新增索引。宽范围本身不能授权删除；窗口内的新 7 天记录即使进入范围，仍会被保存时间／实际过期护栏排除。严格小于当前时间才删除，恰好在边界的记录继续保留至下一次清理。

每条 DELETE 最多删除 5,000 行，但 `LIMIT` **不限制读取行数**。当前库可重复扫描尚未到期的保留行；其读取成本取决于真实表大小及批数，清到最后不足一批时也可能扫描全部剩余记录。历史查询会额外检查索引范围内尚未到期的短窗口记录；混合旧 180 天、新 7 天副本时也可能重复读取这些候选。历史库的 `INDEXED BY raw_message_expiry` 要求索引存在，不自动退化成原始表扫描；有时间边界的范围仍可能很大，不能据此承诺读取恒定为 5,000 行。清理日志分别记录提供方的 `meta.rows_read` 与 `meta.rows_written` 总量；失败或元数据缺失时对应值为 `null`。按真实读写计量核对账户每日额度。

可选 `D1_CLEANUP_MAX_ROWS` 取整数 `1` 至 `200000`，缺省 `60000`，保留原单库最大清理量；示例为 `"35000"`。这是整个调用所有数据库合计的删除上限，最后一批的 LIMIT 会缩小到剩余预算，预算为 1 也不会多删除一行。每库最多 12 条 DELETE，全局最多 40 条；这些是调用级的操作上限，不等于账户每日配额。

短保留策略先连续清理当前库，确认没有到期记录后再把剩余预算分给历史库；如果当前库失败、达到轮数上限或耗尽预算，本轮不抢先清历史积压。历史库之间每库各一轮，再进入下一轮，避免大旧库抢占当前正常保留。默认 180 天保持原来的全部绑定轮询。失败库退出本轮，其他已开始的历史清理继续；完成后 Cron 仍报告失败，避免静默遗漏。日志不包含原始 SQL、绑定数据或凭据。

每日一次运行时，必须给正常上报留出写额度，再确定清理预算；手动触发、多条 Cron 或重试调用会再次获得同样的调用级上限，并没有持久化的每日总预算。索引维护也可能计入写量。监控清理和新增写入的真实计量，不能只用删除条数判断是否低于免费额度。参见 [D1 索引](https://developers.cloudflare.com/d1/best-practices/use-indexes/)和 [D1 定价与计量](https://developers.cloudflare.com/d1/platform/pricing/)。

保留窗口用于判定是否到期，物理删除发生在下一次成功 Cron；每日 Cron 可能让到期副本再保留接近一天，积压或配额不足时更久。监控清理日志和剩余到期行，不把“已配置 7 天”当作“全部旧行已经清完”。

历史绑定只封存新增写入，不暂停当前保留策略的 DELETE。解除绑定前应先确认该库已经清空或安排独立清理，否则这个 Worker 将不再清理或核对其中的数据。累积到九个历史库后，需要另行安排容量及归档，不应删除仍在当前保留窗口内的记录来腾出绑定。

## 切换前封存旧库

“历史绑定不写入”是本 Worker 的路由行为，并不是 D1 权限层的只读授权。旧版本、其他写入器或部署切换期间的在途请求仍可能指向旧库。切换前保存旧配置和 trigger 定义，并在旧库设置插入屏障，防止历史查询后又有旧版本追加同一 ID 的不同内容：

```sql
-- 仅在准备成为历史绑定的旧库执行；当前续写库不要设置此 trigger。
CREATE TRIGGER raw_archive_sealed BEFORE INSERT ON raw_message
BEGIN
  SELECT RAISE(ABORT, 'RAW_ARCHIVE_SEALED');
END;

-- 确认屏障定义已经提交；如果同名 trigger 已存在，先核对定义。
SELECT sql FROM sqlite_master
WHERE type = 'trigger' AND name = 'raw_archive_sealed';
```

该屏障拒绝旧库的所有 INSERT，包括 `INSERT OR IGNORE` 重放。它不授予或限制账户权限，也不阻止管理员 UPDATE／DELETE；应同时停止其他追加写入器。旧库 SELECT 和原有到期 DELETE 仍然可用。先确认屏障已提交，再将新库绑定为 `RAW_DB`、旧库保留为 `RAW_DB_ARCHIVE_1` 等历史绑定。此前已提交的记录由历史查重确认；屏障生效后失败的旧请求不得当成已送达，入库队列保留原 ID 等待新版重试。不要将此封存 trigger 加入通用建库迁移，否则会阻止新库正常续写。

## 回退与容量边界

回退前保存当前队列及新旧绑定清单。新库已有成功确认记录后，不能只恢复不支持历史查重的旧代码，也不能移除新库而忽略其中的数据。若确需回退绑定，应保留支持分库查重的版本；续写库准备转为历史绑定时，也必须先保存其 trigger 定义并安装上述 INSERT 封存屏障，防止新历史库的在途请求继续追加。随后将原库恢复为 `RAW_DB`，把已封存的续写库保留为历史绑定，完成互换并核对后，最后按已保存定义撤销恢复为 `RAW_DB` 的原库屏障：

```sql
-- 仅在已确认恢复为 RAW_DB 的原库执行。
DROP TRIGGER raw_archive_sealed;
```

先解除屏障、后切绑定会重新允许旧版本在途请求向历史库写入，破坏封存前提；先切绑定、后解除屏障期间，原库 INSERT 会暂时失败，队列应继续保留重试。不要提前删除队列、改消息 ID 或将失败回执当成成功。原库如果仍已满，即使解除屏障也不能恢复新增写入；此类回退只能还原配置，不能解决容量问题，通常应修复续写路径并保留新库。

按 [D1 当前限制](https://developers.cloudflare.com/d1/platform/limits/)，Free 账户最多 10 个数据库、总存储 5 GB，单库最多 500 MB；账户中的其他应用数据库也占用这些额度。代码支持九个历史绑定不代表账户还剩九个可建库名额。新建分库可以解决当前单库容量问题，不提高总容量或每日读写额度，也不能保证任意保留窗口长期可持续。应以实际每日新增数据、索引大小和到期清理量核算整个保留窗口所需容量，并提前安排下一次归档及账户容量方案；不要通过提前删除仍在保留期内的数据掩盖积压。
